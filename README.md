# Trao — AI Interview Prep Kit

Turn a pasted job description and a company website into a research-backed interview preparation kit: a company brief, role breakdown, requirement-linked questions, flashcards, and an exactly sized study schedule.

## Stack and architecture

- **Next.js 15 / React 19 / TypeScript**: one deployable app, with the Node.js route handlers providing the backend and the App Router providing protected pages.
- **Tailwind CSS**: responsive interface, with a small set of project-specific CSS tokens for the visual system.
- **Local JSON persistence**: a deliberately dependency-light store at `DATA_DIR/trao-store.json` keeps accounts, kits, edits, generated/edited/pinned state, and practice scores together. This is suitable for a single Node instance with persistent disk; use a persistent volume in production. It is not a multi-instance database.
- **Gemini 2.0 Flash (optional)**: set `GEMINI_API_KEY` to enable model-assisted extraction and generation. The app uses a deterministic, source-constrained fallback when the key is absent or a provider call fails, so the batch command is runnable without a paid service or credential.

The main pipeline is in `src/lib/pipeline.ts`; retrieval, model calls, schema/coverage/scheduling, authentication, and persistence are separate modules. Both the UI and `npm run evaluate` call this same pipeline.

## Local setup

Requirements: Node.js 22 or later and npm.

```sh
npm install
copy .env.example .env
npm run dev
```

Open <http://localhost:3000>, register an account, and build a kit. Set a random `SESSION_SECRET` of at least 32 characters before deploying. `DATA_DIR` defaults to `./data`; choose a persistent writable directory for production. `APP_URL` documents the public app origin. `GEMINI_API_KEY` is optional.

To run automated tests and the production build:

```sh
npm test
npm run build
```

## Batch evaluation

The required command reads an array of `{ "id", "jd", "company_url", "days" }` cases and writes one output object with `version`, `generated_at`, and one `ok` or `failed` entry per case:

```sh
npm run evaluate -- --input cases.json --output kits.json
```

The same retrieval, generation, validation, coverage, and scheduling functions are used as in the app. Cases are processed independently and failures are recorded without stopping later cases. `days` must be an integer from 1 to 60. Local and loopback company URLs are supported outside production to make local test fixtures possible; production rejects private and loopback addresses.

## Research and generation sequence

1. Parse the supplied company URL, fetch only HTTP(S) HTML within a 1 MB limit, follow a bounded number of redirects, retry transient failures, and apply `robots.txt`. Only same-origin links are considered.
2. Crawl the homepage and rank discovered links by visible link text/path for hiring, careers, recruiting, interview, handbook, about, and product evidence. This ranking is link-driven, not a hard-coded page-path list. Unavailable or irrelevant pages are skipped and do not fail a kit.
3. Extract only requirements and responsibilities present in the pasted description. Explicitly optional wording maps to `nice`; other extracted requirements map to `must`. A short or vague posting is allowed to yield no requirements.
4. Search DuckDuckGo's public HTML results for public discussion of the company's interview process. Search results are treated as leads, not verified claims. Missing results are reported through the absence of discussion evidence.
5. Summarize retrieved company pages without treating their text as instructions. Generate questions separately by technical, behavioural, system-design, and company-fit category, using the role requirements and any hiring-process evidence.
6. Application code compares question requirement IDs against must-have IDs. Any uncovered must-have is given a deterministic, directly linked fallback question, then coverage is checked again. The kit records `passes: 2`; no model is trusted to declare coverage.
7. Application code allocates every question to exactly the number of requested days. Must-have-linked and harder questions are ordered earlier; day count and minute values are integer-validated. No schedule is generated by a prompt.
8. Validate the final kit against the Appendix A field names and referential integrity before returning or saving it.

The retrieval bot identifies itself as `TraoInterviewPrepBot/1.0`, waits between company-page requests, caps requests and response sizes, and skips sources it cannot read. Company-page and search-result text is always passed as untrusted data. The public discussion search uses DuckDuckGo HTML; company website pages come only from the user-supplied origin.

## Editing, regeneration, and practice

The kit remains in the Appendix A shape. UI metadata lives alongside it in the stored record: each question and flashcard is marked `generated`, `edited`, or `pinned`. Inline edits save automatically. Regenerating a question category retains edited and pinned questions and refreshes only generated questions in that category; regenerating the company brief or schedule changes only that section. Practice records one confidence score (1–5) and timestamp per flashcard; the next practice round sorts unseen and lower-confidence cards first.

## Authentication and security

Registration and login use PBKDF2 password hashes and a signed, HTTP-only, SameSite=Lax session cookie. Protected pages and API handlers check the session, and all kit reads/writes/deletes are scoped to its owner. Sessions expire after seven days. Set `SESSION_SECRET` to a unique random value for production. No email verification or password reset is included.

External URLs reject non-HTTP(S) schemes and embedded credentials. Production rejects hosts resolving to private/loopback addresses; redirects are revalidated. Retrieval accepts HTML only, enforces page limits, uses request timeouts and retries, and avoids off-origin crawl links. This assessment implementation is intentionally single-instance; the file store is not a substitute for a transactional database or a multi-instance deployment store.

## Deploy

Build and start the app with `npm run build` and `npm start`, then set `SESSION_SECRET`, `DATA_DIR`, and optionally `GEMINI_API_KEY` in the host's secret/environment settings. Attach persistent storage at `DATA_DIR`. The app combines frontend and backend in one Node service, so both are reachable from its public URL. Do not commit `.env` or the data directory.

The public Git repository can be used as the source for a free Node hosting service that supports a persistent volume. A live URL requires provisioning that host and its persistent storage; no deployment credentials are included in this repository.

## Design decisions and limitations

- JSON storage avoids making a database service or key a prerequisite for cloning and running the required batch command, but is appropriate only for a single process/instance and modest local data.
- The model is optional to keep evaluation repeatable and credential-free. The fallback intentionally prefers an honest thin kit over inferred requirements; it is less nuanced than the model-assisted path.
- The external discussion search may be unavailable or return noisy results; no discussion result is treated as authoritative evidence.
- Robots rules and DNS checks reduce retrieval risk; as with ordinary hostname-based HTTP clients, a production deployment should additionally use outbound network controls to protect against DNS rebinding and provider-specific egress behavior.
- A public application URL and a 3–4 minute walkthrough recording must be supplied by the submitter after deploying and demonstrating the app.
